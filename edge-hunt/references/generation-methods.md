# Механика генерации корнеров

Читать после фиксации нормального контракта. Цель — получить сценарии, которые
не возникают из линейного чтения тикета.

## 1. Классы внутри измерения

Разделить каждую релевантную ось на классы, при которых поведение действительно
может различаться.

Пример для состояния документа:

- чистый и сохранённый;
- есть локальные изменения;
- открыт старый снимок;
- удалён или изменён в другом месте.

Пример для ответа сервера:

- успех сразу;
- успех после задержки;
- явный отказ до записи;
- запись произошла, ответ потерян;
- частичный успех нескольких операций.

Не использовать классы `обычное / необычное`: они не подсказывают разных веток
поведения. Для чисел и размеров брать значения по обе стороны реальной границы,
а не абстрактные «очень большие данные».

## 2. Пересечения

Сначала проверить каждое значение отдельно, затем пары между разными осями:

`состояние × действие`

`данные × время`

`роль × способ входа`

`устройство × свежесть данных`

Не перебирать декартово произведение целиком. Выбирать сочетания, где два
условия управляют одной веткой, делят состояние или находятся по разные стороны
границы компонента. Для особенно дорогого ущерба добавлять тройки.

Эмпирическая опора: NIST описывает interaction rule — большинство известных
отказов вызывается небольшим числом взаимодействующих факторов; covering arrays
позволяют покрывать такие сочетания без полного перебора:
<https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/combinatorial-methods-in-testing/interactions-involved-in-software-failures>.

## 3. Последовательности

Для действий, меняющих общее состояние, построить короткие цепочки длиной 2–4:

- `A → B` и `B → A`;
- `A → A`;
- `A → отмена → A`;
- `A → B → назад`;
- `A → прерывание → продолжение`;
- `A началось → B изменило состояние → A завершилось поздно`.

Проверять не только финальное состояние, но и то, что осталось доступно после
каждого шага. У двух корректных действий может быть некорректный порядок.

Для event-driven систем NIST предлагает sequence covering arrays, покрывающие
разные порядки коротких наборов событий:
<https://www.nist.gov/publications/combinatorial-methods-event-sequence-testing?pub_id=906770>.

## 4. Жизненный цикл

Первое успешное выполнение часто проверяет только пустое состояние. Повторить
тот же контракт в следующих точках:

- первый объект → второй → много существующих объектов;
- первая сессия → restart → восстановленная сессия;
- сразу → после истечения TTL, токена, кэша или дедлайна;
- до update → после update или миграции данных;
- право выдано → отозвано → выдано снова;
- интеграция настроена → внешний контракт или scope изменился.

Для внешней системы не угадывать её гарантии. Проверить актуальную документацию:
срок жизни, повторяемость запроса, семантику replace/merge, порядок доставки,
пагинацию, лимиты и поведение после отзыва доступа.

## 5. Инварианты и преобразования

Сформулировать 1–3 свойства, которые должны пережить изменение. Затем применить
к сценарию преобразование и проверить, обязано ли свойство сохраниться.

Полезные преобразования:

- повторить тот же запрос или клик;
- отменить и выполнить снова;
- задержать ответ;
- переставить независимые действия;
- открыть тот же объект другим путём;
- перейти на другое устройство или вкладку;
- заменить данные эквивалентными;
- добавить посторонний объект, не относящийся к операции;
- закрыть временный контекст и вернуться к основному.

Примеры инвариантов:

- повтор не создаёт второй объект;
- отмена не оставляет скрытый побочный эффект;
- временный просмотр не уничтожает основную работу;
- поздний ответ не перезаписывает более новое состояние;
- один и тот же объект сохраняет идентичность во всех точках входа;
- отзыв права действует и для уже открытого экрана.

Metamorphic testing строит новые проверки из необходимых отношений между
несколькими входами и результатами, когда точный результат трудно задать:
<https://i.cs.hku.hk/~tse/Papers/2010s/hlmtCSUR.html>.

## 6. Разрезы сбоя

Найти момент необратимого эффекта: запись, отправка, списание, публикация,
удаление, выдача права. Разместить сбой в трёх точках:

1. эффект ещё не начался;
2. часть эффекта уже произошла;
3. эффект завершён, подтверждение потеряно.

Для каждой точки спросить:

- что видит человек;
- что сохранено фактически;
- безопасен ли повтор;
- как система различит «не сделано» и «сделано, но ответ потерян»;
- можно ли восстановиться без ручного вмешательства.

## 7. Параллельность

Добавлять эту ось только при реально общем состоянии. Проверить:

- два одинаковых действия одновременно;
- изменение и удаление одного объекта;
- старый экран сохраняет поверх нового;
- право отозвано во время операции;
- два воркера повторно обрабатывают одно событие;
- результат старой операции приходит после новой.

Не писать просто «race condition». Назвать два участника, их исходное состояние,
порядок видимых эффектов и допустимый итог. Систематическое исследование разных
расписаний — основа concurrency testing вроде Microsoft CHESS:
<https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2007-149.pdf>.

## 8. Сверка с реальностью

Искать материал для осей не только в постановке:

- ветки и guards в коде;
- существующие тесты и отсутствующие соседние комбинации;
- состояния загрузки, ошибки и отмены в интерфейсе;
- история багов, откатов и продуктовых решений;
- форматы данных и ограничения базы;
- гарантии и поведение внешнего API;
- логи и реальные способы использования.

Факт из артефакта сильнее универсальной эвристики. Если конкретная ось ничем не
подтверждена и не следует физически из изменения, не включать её для полноты.

Способ проверки должен наблюдать тот же слой, где ожидается дефект:

- пиксели и фокус — в живом интерфейсе;
- сохранность — чтением из постоянного хранилища после restart;
- доставка — на принимающей стороне, а не по факту отправки;
- права — запросом от конкретной роли после выдачи и отзыва;
- повторяемость — реальным повтором после потерянного ответа.

Если проверка не может физически увидеть дефект, её зелёный результат ничего не
говорит об этом корнере.

## Пример: временный просмотр поверх основной работы

Нормальный контракт: `задачи открыты на весь экран → открыть вспомогательную
секцию → посмотреть → закрыть → задачи остались как были`.

Оси:

- основной режим: обычный / fullscreen;
- тип открываемой секции: основная / вспомогательная;
- место открытия: заменить область / временная панель;
- следующее действие: продолжить / закрыть / открыть ещё одну секцию.

Неочевидное пересечение: `fullscreen × вспомогательная секция × замена области ×
закрытие`. Каждая часть по отдельности нормальна, но вместе нарушает инвариант
«временный просмотр не уничтожает основную работу». Это корнер уровня модели,
а не ещё одно состояние ошибки интерфейса.

## Отсечение шума

Удалить сценарий, если:

- он невозможен по проверенному ограничению;
- его полностью обрабатывает неизменяемый нижний слой;
- он не меняет ожидаемое поведение;
- он относится к другой задаче и безопасно откладывается;
- невозможно объяснить, какие реальные оси его породили.

Сильный результат — не много случаев, а несколько ситуаций, которые меняют
контракт, реализацию или способ проверки.
